# Hand-Drawn Figures — Drawing Specification

Eight diagrams. None touches data, so none can be generated by script; both reference theses drew
their architecture and framework diagrams the same way and used code only for results.

Draw in **draw.io desktop**. Export **PNG at 300 dpi**, transparent background off, white background
on. One file per exhibit, named `figNN_MM_slug.png`, saved into `figures/` at the repository root
beside the plotted set. Keep the `.drawio` sources in `figures/drawio_sources/` so a diagram can be
edited later without redrawing it.

Avoid presentation-design tools. They produce decorative output that reads as unserious in a
technical report.

---

# 0 · Conventions that apply to every diagram

**Colours**, taken from `src/figures/palette.py` so the drawn set and the plotted set look like one
document:

| Role | Hex | Used for |
|---|---|---|
| Data and inputs | `#4C72B0` | recordings, arrays, anything that arrives rather than is computed |
| Neutral processing | `#8C8C8C` | transformation steps that are not the contribution |
| The contribution | `#B8860B` | the three readouts, the fusion, the change-point stage |
| Outputs and decisions | `#55A868` | detected intervals, results, deliverables |
| Problems and exclusions | `#C44E52` | the dropped branch, the failure mode in Fig 2.13 |

Fill each box white and use the colour for the **border and the heading text only**. Solid colour
fills print heavily and read as slides. Border weight 1.5 pt.

**Type.** Serif throughout, matching the plotted figures. Box headings 11 pt bold, body text 9 pt,
arrow labels 8 pt italic. Never smaller than 8 pt — at print size it disappears.

**Arrows.** Plain single-headed, 1 pt, dark grey `#8C8C8C`. Orthogonal routing, not curved. Label an
arrow only when the transformation is not obvious from the two boxes it connects.

**No figure number and no title inside the image.** The report's caption carries both. This is the
same rule the plotted figures follow.

**Every number on a diagram comes from the record.** The three that matter are called out in the
relevant sections below. If a number is not specified here, do not invent one — leave it off and ask.

# Fig 1.5 — Research framework

Chapter 1. Three columns, arrows left to right between columns.

**Column 1, Objectives** — four stacked boxes, data colour:

1. Detect seizure intervals without using seizure labels
2. Transfer across patients without per-patient tuning
3. Indicate which channels drive a detection
4. Demonstrate the approach in a clinical review interface

**Column 2, Methods** — four boxes, contribution colour, one aligned with each objective:

1. Graph autoencoder trained on background activity, three anomaly readouts, change-point detection
2. Patient-wise data partition, one model for all patients, label-free operating point
3. Per-node reconstruction error, standardised against each patient's own background
4. Browser-based review application recomputing scores on the continuous recording

**Column 3, Outputs** — four boxes, output colour:

1. Event-level detection performance on held-out patients
2. Per-patient results and failure analysis
3. Provisional channel attribution, validated on synthetic injections
4. Working prototype and its architecture

Horizontal arrows objective → method → output, one row at a time. No arrows between rows: the four
lines are parallel, not sequential, and drawing them as a chain would misstate the design.

# Fig 2.6 — Autoencoder architecture

Chapter 2. The one diagram in the set that carries dimensions, so it is the one where a wrong number
is most visible.

Left to right:

**Input**, data colour. Two stacked labels inside one box:
- `Node features: 18 adjacency-row entries + 5 log band powers = 23 per node`
- `18 nodes per window`

**Encoder**, contribution colour, two blocks in sequence:
- `Graph convolution 23 → 64`
- `Graph convolution 64 → 16`

**Latent**, contribution colour, one box: `Latent node representation, 16 dimensions × 18 nodes`.

**Decoder**, two branches from the latent box:
- upper: `Inner product` → `Reconstructed adjacency, 18 × 18`
- lower: `Fully connected 16 → 32` → `Fully connected 32 → 5` → `Reconstructed band powers, 5 per node`

**Loss**, output colour, receiving both reconstruction boxes:
`Mean squared error on adjacency + 0.1 × mean squared error on node features`

Below the diagram, one line: **Total trainable parameters: 3,285.**

**That number is 3,285.** A figure of roughly 8.7k circulates in this project's notes and in the
training script's own docstring. It is wrong and inconsistent with the checkpoint's file size. It
must not appear.

# Fig 2.7 — Three readouts from one encoder

Chapter 2. The core contribution diagram.

One box at the top, contribution colour: `Trained encoder (shared, frozen)`. Three arrows down into
three parallel branches, each a column of two boxes:

| Branch | Upper box | Lower box |
|---|---|---|
| Left | Reconstruction error — mean squared error between input and reconstructed graph | Per-window scalar |
| Centre | Latent Mahalanobis distance — distance from the patient's own background distribution in the 16-dimensional latent space | Per-window scalar |
| Right | Gamma-band amplitude coupling — spectral coupling anomaly in the 30–60 Hz band | Per-window scalar |

Under the three lower boxes, one box spanning all three: `Robust standardisation, per branch, against
each patient's own background`.

Under that, one box: `Equal-weight fusion, one third each`.

Under that, output colour: `Fused anomaly score, one value per window`.

**Three branches, never four.** A recurrent temporal branch was part of an earlier design, was
dropped because its training code could not be recovered, and was replaced by the latent readout —
that replacement is the contribution this diagram exists to show. The recurrent branch must not
appear anywhere in the report, including as a greyed-out or crossed-through box. If you want to show
that something was replaced, do it in the text, not by drawing the thing that is not there.

Beside the centre branch, a small italic note: *label-free: the background distribution is fitted per
patient without using any annotation.*

# Fig 2.11 — Attribution scoring and the injection scheme

Chapter 2. Two panels side by side, separated by a vertical rule, each with a small heading in bold
at its top-left: `(a) Scoring` and `(b) Synthetic validation`.

**Panel (a), top to bottom:**

1. `Reconstruction error per node` — 18 values per window, data colour
2. `Standardise each node against that patient's own background` — neutral
3. `Aggregate over the seizure window, 95th percentile` — neutral
4. `Ranked channel list for one seizure` — output colour

**Panel (b), top to bottom:**

1. `Take a contiguous background block; draw its length from the real seizure duration distribution`
2. `Multiply the per-node error on |S| chosen channels by α`
3. `Grid: α ∈ {1.00, 1.25, 1.50, 2.00, 3.00} × |S| ∈ {1, 2, 4, 8, 12}, 200 replicates per cell`
4. `Score with panel (a) and check whether the injected channels are recovered` — output colour

Between the panels, one italic line: *the injected channels are known exactly, which the recordings
never provide.*

**One caveat to carry into the caption**, not onto the diagram: the diffuseness experiment used a
different grid, `|S| ∈ {1, 2, 4, 12, 18}`. Panel (b) shows the discrimination grid. The caption says
which.

# Fig 2.13 — Why stored scores cannot be replayed on a time axis

Chapter 2. The hardest of the eight, and the most valuable — it justifies the application's whole
architecture and it now has measured numbers behind it.

Three rows, each a horizontal bar representing the same recording, drawn to the same width and
aligned so a reader can read down a column.

**Row 1 — `The recording as it exists`.** One continuous bar, data colour, subdivided by thin ticks
into windows. Small red segments marked `rejected` scattered along it, and two wider segments in the
seizure colour marked `seizure`. Label at the right end: `every window has a position in time`.

**Row 2 — `The stored score array`.** A shorter bar, same tick size, showing only the surviving
windows packed together with no gaps. Label: `ordered by segment; the rejected windows are gone and
nothing records where they were`. An arrow from row 1 to row 2 labelled *artifact rejection removes
windows*.

**Row 3 — `The reconstructed timeline`.** A bar the same width as row 1, in two visibly different
parts: the left part drawn from the stored scores and labelled `real scores, shifted from their
original positions`, and the right part hatched or lightly shaded in the problem colour and labelled
`bootstrap-resampled — the stored array has run out`. The boundary between the two parts sits at
about 40 % of the width. An arrow from row 2 to row 3 labelled *rebuilt using the annotation file*.

Below the three rows, a small box in the problem colour with three lines. **These are measured
values; use them exactly:**

- `Across the eight held-out patients, on average 53.9 % of each reconstructed timeline carries a resampled score, ranging from 40.0 % to 66.9 %.`
- `For one patient the stored background array holds 12,452 scores against 25,224 positions.`
- `The false-alarm rate is measured on these timelines. The direction of the resulting bias is not established.`

That last sentence matters. Do not write that the bias is small, or conservative, or that it does not
affect the conclusions. It has not been quantified, and saying so plainly is the honest position and
the defensible one.

7. Fig 2.12 — bands plus the forbidden-path marker
8. Fig 2.13 — the measured numbers must be exact

Send them to me in one batch when the first four are done, and again for the last four. Reviewing
eight unfamiliar diagrams at once means the same mistake gets found twice instead of once.
